# Results Dashboard

## Purpose

Show each finished pool week's results as a visual page the owner can open
from a phone or laptop, at home or away, on Tuesday morning. If it reads
better than the Markdown report, it replaces that report later; this design
keeps both.

The page answers the same questions as the weekly results report
(`2026-09-15-weekly-results-tracking-design.md`): how the week went, whether
the model or the submissions caused it, and how we stand against the field.
It adds what Markdown shows poorly: season trends and uncertainty drawn as
intervals.

## Decisions already made

| Question | Decision |
|---|---|
| Audience | The owner only. The page carries other entrants' results, so it is never public. |
| Content | The weekly report plus season views (option B of the brainstorm). No in-week live view, no drill-down browsing. |
| Build | A static page generated by the Tuesday job. No web application and no query-time database access. |
| Access | Tailscale `serve` from this machine, private to the owner's tailnet. Never `funnel`. |
| Layout | One scrolling page: the week's headline first, the season below it (mockup option A). |

Tailscale is installed and signed in on this machine (`sandbox`) and the
owner's laptop. MagicDNS and HTTPS certificates are enabled, and the operator
user is `jmiller`. The dashboard address is
`https://sandbox.tail750bff.ts.net/pickem/`.

## Architecture

```
pickem-results timer → fetch-results.sh → import-results / results-report
                                               │
                                    build_results_report()   (unchanged)
                                               │
                        ┌──────────────────────┴──────────────────────┐
             results_markdown.py (kept)                    results_html.py (new)
             <NAS>/results/week{N}-report.md               <dashboard dir>/week-{N}.html
                                                           <dashboard dir>/index.html
                                                                      │
                                                           tailscale serve /pickem
```

`ResultsReport` is the only interface between the grading and the renderers.
The HTML renderer reads it and nothing else; it knows nothing about DuckDB,
CBS, or Discord.

## Component 1: renderer — `src/pickem/report/results_html.py`

```python
def render_results_dashboard(
    report: ResultsReport,
    *,
    generated_at: datetime,
    other_weeks: Sequence[int],
) -> str
```

A pure function that returns one self-contained HTML document. `other_weeks`
is the list of imported pool weeks, used for the links at the foot of the
page.

### Self-contained

- All CSS is inline and the page makes no external requests: no fonts,
  scripts, or images from any host. It renders offline and identically on
  every load.
- Charts are inline SVG generated in Python. There is no JavaScript. The
  folded game table and glossary use native `<details>`.
- Every value interpolated into the page is HTML-escaped.

### Sections, top to bottom

Every figure comes from a field or function `ResultsReport` already exposes
(`standings`, `week_games`, `season_games`, `record_for`, `clv_summary`,
`findings`, `BACKTEST_TIER_RATES`). No new statistic is computed.

1. **Headline.** Stat tiles for points out of games, rank of entrants, field
   median, winner's points, and gap to the winner, from this week's
   `WeekStanding`. One line per board beneath: our points against the board
   median and best (`BoardStanding`).
2. **This week, by board.** For each board, a table of us / model / field
   consensus / close divergence records. Beneath it, a folded game table
   (`<details>`), one row per game ordered by kickoff: matchup, CBS line,
   final score, our side and result, the model's side, tier and result, the
   field's split, and two markers: *disagreed with the model* and *against the
   field* (`GradedGame.against_field`).
3. **Season trend.** Two charts by pool week, over every week in
   `report.standings`: our points against the field median and the winner's
   points; and the share of the field we beat (`beat_share`). A single week
   draws points without lines.
4. **Model by tier.** Horizontal bars of the model's hit rate by sport and tier
   over the season, each with its 95% Wilson interval as a whisker and a tick
   at the backtest expectation from `BACKTEST_TIER_RATES`. CFB rows are
   labeled "NFL backtest". Each row shows its record and n.
5. **Us against baselines.** A dot-and-interval chart of each strategy in
   `Strategy` over the season's decided games, with n. A strategy that sits a
   game out has a smaller n, as in the Markdown.
6. **Closing-line value and against the field.** Stat tiles: mean CLV with its
   interval, share of picks with CLV > 0, n; and the record of our
   against-the-field picks.
7. **What the data says.** The claims and "not distinguishable yet" lines from
   `findings(report.season_games)`, the same function the Markdown uses.
8. **What the terms mean.** The strategy glossary, folded.
9. **Other weeks.** Links to `week-{N}.html` for every entry in `other_weeks`.

### Charts

- One linear scale per chart places every mark, whisker, tick and label. Rate
  charts run 0–100% with a 50% reference line.
- Chart text and marks take their colors from the page's CSS tokens, so they
  read in light and dark themes.
- A chart with nothing to draw (for example, the NFL board in pool week 1)
  shows "No games yet" instead of an empty axis.
- A rate with n = 0 prints "—", never 0%.

### Presentation

- Light and dark themes from `prefers-color-scheme`, defined as CSS tokens.
- Readable at 400 px wide with a 16 px side gutter. Wide tables scroll inside
  their own container; the page body never scrolls sideways.
- Rates print as in the Markdown: `W–L (P) = xx.x% [lo–hi], n`.

### Shared glossary

The strategy definitions move from `results_markdown._DEFINITIONS` to
`results.STRATEGY_DEFINITIONS: dict[Strategy, str]`, as plain text with no
Markdown markup. The Markdown renderer formats each as `**term** — text`;
the HTML renderer as a definition list. The only wording change is dropping
the backticks around `model` in the first-sheet definition.

## Component 2: writing the pages

### Location

The dashboard directory is `config.DASHBOARD_DIR`, from the environment
variable `PICKEM_DASHBOARD_DIR`, defaulting to
`~/.local/share/pickem/dashboard`. It is local, not on the NAS, so the page
stays reachable when the NAS is offline. It is created on first write.

### Files

- `week-{N}.html` — that pool week's page. Its season sections cover the
  season through week N, so an older page stays an accurate record of that
  point in the season.
- `index.html` — a copy of the latest imported pool week's page.

### Writing

`_write_results_report` in `cli.py`, which both `import-results` and
`results-report` call, writes the dashboard after the Markdown:

1. Render the page.
2. Write it to a temporary file in the dashboard directory, then rename it to
   `week-{N}.html`.
3. If N is the latest imported pool week (`store.pool_weeks(season)[-1]`),
   write `index.html` the same way. Rebuilding an older week never changes
   `index.html`.
4. Log `dashboard_written` with the pool week, path and size in bytes.

When a new week is imported, the earlier weeks' pages are not rewritten, so
their "other weeks" links do not include it. `index.html` always lists every
imported week. This is accepted: the index is the entry point.

### Failure

The import and the Markdown are written before the dashboard, so a dashboard
failure never loses them. On a render or write failure the command logs
`dashboard_write_failed` with the error type and detail, prints the reason,
and exits nonzero, as a failed DM does today. The DM is still sent first:
`_write_results_report` returns the dashboard failure instead of exiting, the
command sends the DM (which then omits the dashboard link), and only then
exits nonzero. `fetch-results.sh` already DMs the owner when the import step
exits nonzero, so the failure itself is also reported.

## Component 3: the Discord DM

A new optional setting, `PICKEM_DASHBOARD_URL` (for example
`https://sandbox.tail750bff.ts.net/pickem/`), read by `config.dashboard_url()
-> str | None`. When it is set, `build_results_embed` adds a link to
`<url>week-{N}.html`. When it is unset, the embed is unchanged. The Markdown
path stays in the embed.

## Component 4: serving

Served by Tailscale; this project adds no server process or systemd unit.

```
tailscale serve --bg --set-path /pickem ~/.local/share/pickem/dashboard
```

Tailscale persists the serve configuration across reboots. Only devices signed
in to the owner's tailnet can reach it. `tailscale funnel` would expose it to
the internet and must not be used.

### Runbook — `docs/runbooks/dashboard.md`

- Adding a device: install Tailscale and sign in with the same account.
- Enabling serving (the command above) and checking it: `tailscale serve
  status`, then open the address.
- Setting `PICKEM_DASHBOARD_URL` in `.env`.
- Rebuilding a page: `pickem results-report --season 2026 --pool-week N`.
- Turning serving off: `tailscale serve --set-path /pickem off`.
- When the page will not load: the machine is off or Tailscale is
  disconnected on either end. The DM and the NAS Markdown remain available.

The README's results section gets a short pointer to the runbook.

## Logging

Following the `logging-standards` skill and `pickem.obs.log`:

- `dashboard_written`: pool week, path, bytes, and whether `index.html` was
  updated.
- `dashboard_write_failed`: pool week, error type, error detail.

## Out of scope

- Dropping the Markdown report. That is a later, one-line decision once the
  dashboard has proven itself.
- Public or shared access, logins, and cloud hosting.
- In-week live recommendations and interactive drill-down.
- Monitoring that the page is reachable.

## Testing

Built test-first, reusing `tests/results_helpers.py` to build reports.

### Renderer — `tests/test_results_html.py`

- Every section is present; the headline tiles hold this week's figures; the
  game table has one row per week game.
- The *disagreed with the model* and *against the field* markers land on
  exactly the games that qualify.
- Charts are drawn to scale: a known rate's mark sits at its expected x
  coordinate; whiskers span the Wilson bounds; backtest ticks sit at 63.7,
  54.2 and 49.5%.
- Sparse data: a pool week with one board shows "No games yet" for the other;
  n = 0 prints "—"; a one-week season draws a trend without lines.
- Team names and other text are HTML-escaped.
- Self-contained: no `src` attribute and no `<script>` or `<link>` element;
  the only `href` values are relative `week-{N}.html` links.
- The "other weeks" links match `other_weeks`.
- Findings text on the page equals the text `findings()` produces, the same
  source the Markdown uses.

### Shared glossary — `tests/test_results_markdown.py`

- The existing glossary test passes against `STRATEGY_DEFINITIONS`, and every
  `Strategy` has a definition.

### Writing and DM — `tests/test_results_cli.py`

- `import-results` writes `week-N.html` and `index.html` into the dashboard
  directory.
- `results-report` for an older week writes `week-N.html` and leaves
  `index.html` unchanged.
- A render failure keeps the Markdown and the imported rows, still sends the
  DM without the dashboard link, and exits nonzero.
- The embed carries the week's link only when `PICKEM_DASHBOARD_URL` is set.

### Real pages — `tests/test_results_real_pages.py`

- When the private saved pages are present, render every imported real week
  and check the output parses as HTML with every section. Skipped otherwise.
